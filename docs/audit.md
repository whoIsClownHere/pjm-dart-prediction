## 1. Целостность данных

### Где вычисляется `dart`

`scripts/data/data_collection.py:60` — `out["dart"] = out["da_lmp"] - out["rt_lmp"]`.
Единственное место, где `dart` считается. Правило README §3 (никаких операций
кроме вычитания) пока не нарушено.

### Тип join между DA и RT

Не `merge`, не `merge_asof`, не явный `join`. В `get_dart_data`
(`scripts/data/data_collection.py:50-59`) DataFrame строится из словаря двух
Series (`da["lmp"]`, `rt["lmp"]`, …) — pandas выравнивает их по **объединению
индексов** (эквивалент outer join), а не по явной сетке дат. На практике это
означает: час попадёт в результат, если он есть хотя бы в одном из `da`/`rt`.
Если API не вернёт час ни в одном из двух ответов, этот час не появится вовсе
— ни как NaN, ни как пропуск в подсчёте, потому что нет `reindex` на
`date_range(freq="h")`. Замер по текущим файлам:

```
raw dart_data (train+test):        66 456 строк
ожидаемая полная почасовая сетка:  66 456 строк
пропущено при слиянии:                  0
```

То есть на **текущем экспорте** скрытых пропусков от слияния нет — судя по
недавним коммитам (`03cfbbd`, `c5f4d40`, «The correct way to collect DART
baseline data»), сбор данных уже переделан. Но защиты в виде явного
`reindex` в коде всё ещё нет: если API вернёт неполный ответ, час просто
исчезнет молча. README §3 п.1 (претензия про 7593 пропавших часа из 66287)
описывает, по всей видимости, более старый экспорт — к текущим
`dart_data_train.csv` / `dart_data_test.csv` эта цифра не относится
дословно, но риск, который правит Фаза 1 (`outer join + reindex`), реален
и не закрыт нынешним кодом.

### Где строка удаляется по значению таргета

Прямого `dropna()`/`clip()` на колонке `dart` в `scripts/` нет. Но есть два
косвенных места:

1. **`scripts/data/features.py:81-82`** — `build_features` кладёт сырые
   `rt_lmp` и `da_lmp` в матрицу признаков `out`, а на `features.py:84`
   вызывается `out.dropna()` по всей матрице. Поскольку `dart = da_lmp -
   rt_lmp`, а `da_lmp`/`rt_lmp` — компоненты таргета, этот `dropna()`
   косвенно требует полноты таргета для каждой строки. Отдельно от таргета
   такой dropna не считается (нарушение правила README §3 «раздельно по
   признакам и по таргету»).
2. **`analysis/models.ipynb`, cell 8** — явный вызов `mask_iqr_outliers` на
   `rt_lmp` и `da_lmp` (не на `dart` напрямую, но эквивалентно, так как
   выброс в любом из них почти всегда означает выброс в `dart`). Результат
   сохраняется в `features.csv` в cell 14 (`feature.to_csv('features.csv')`).
   **Это и есть источник обрезанного `features.csv`, который описан в
   README.** Числа сошлись почти точно:

```
до маски:                     66 120 строк   (после build_features().dropna())
после mask_iqr_outliers:       58 694 строки
потеряно:                       7 426 строк   (README называет 7 593 — тот же порядок,
                                                разница объясняется чуть другим окном
                                                train/test в момент замера)

dart до маски:   min=-3977.23  max=1075.26
dart после маски: min=-74.63   max=77.20      (README: диапазон таргета «±77.20» —
                                                совпадает буквально)
```

`mask_iqr_outliers` (`scripts/data/features.py:15-26`) применяется к
**Series**, не к DataFrame и не к таргету напрямую — вызывающий код
(`analysis/eda.ipynb` cell 16 и `analysis/models.ipynb` cell 8) вручную
собирает булеву маску из `rt_lmp`/`da_lmp` и режет ей весь датафрейм,
включая `dart`.

### Скрытая потеря строк на границе train/test

`build_features` (`scripts/data/features.py:87-98`) вызывается **отдельно**
для `train` и для `test` (`save_model_inputs(train, …)`,
`save_model_inputs(test, …)` — каждый на своём CSV). Лаги и роллинги внутри
`build_features` требуют до 168 часов истории. Так как train и test строятся
из разных DataFrame, а не из одной непрерывной серии с последующим сплитом,
warmup срабатывает **дважды**: в начале train и в начале test — то есть
первая неделя test-периода теряет `dart_lag_168` и аналоги, хотя нужная
история физически есть (лежит в конце train). Замер:

```
raw (train+test):                    66 456 строк
после build_features (train, test отдельно): 66 120 строк
потеряно:                                       336 строк
```

Все 336 потерянных строк — это ровно первая неделя train (`2019-01-01` —
`2019-01-08`, 168 часов) и первая неделя test (`2026-01-01` — `2026-01-07`,
168 часов). Второй кусок — чистая потеря, которой не было бы при
непрерывном построении признаков с последующим сплитом. При переходе на
трёхчастный сплит (Фаза 4: train/validation/test) эта проблема повторится
на **двух** границах вместо одной, если способ построения не поменять.

## 2. Признаки

### Что реально производит текущий код

`scripts/data/features.py:build_features` (36-84) на выходе даёт (проверено
по колонкам `train_features.csv`):

```
hour_sin, hour_cos, dow_sin, dow_cos, is_weekend,
month_1 … month_12                              (12 dummy-колонок)
dart_lag_1, dart_lag_2, dart_lag_3, dart_lag_24  (cutoff-anchored, см. ниже)
rt_lmp_lag_1, rt_lmp_lag_24                      (cutoff-anchored)
dart_lag_48, dart_lag_168                        (row-anchored, .shift(n))
rt_lmp_lag_48, rt_lmp_lag_168                    (row-anchored, .shift(n))
dart_mean_24, dart_std_24, dart_mean_168         (cutoff-anchored rolling)
rt_lmp, da_lmp                                   (сырые уровни — компоненты таргета)
```

31 колонка признаков (без учёта `dart`-таргета) — совпадает с числом «31»,
которое README называет как размер старого набора. `mask_iqr_outliers` из
`features.py` используется только для читки `rt_lmp`/`da_lmp` в ноутбуках,
самим `build_features` не вызывается.

### Критичная находка: `rt_lmp`/`da_lmp` как «признаки»

`features.py:81-82` кладёт сырые `rt_lmp` и `da_lmp` прямо в матрицу `X`. Это
буквальные компоненты таргета (`dart = da_lmp − rt_lmp`) — модель, обученная
на них напрямую, тривиально реконструирует таргет. Сейчас это не взрывается
только потому, что их вручную выпиливают в `analysis/models.ipynb` cell 10
(`feature.drop(columns=["rt_lmp", "da_lmp"])`) **перед** обучением Ridge —
но это ручной шаг в ноутбуке, не часть `build_features`. Любой новый путь
(например, прямой вызов `build_features` для классификации), который
забудет этот `drop`, получит утечку таргета. Это должно быть исправлено в
Фазе 3 — эти колонки не должны генерироваться `build_features` вовсе, а не
вычищаться постфактum.

### Два разных механизма лагов — путаница в названиях

В коде есть **два независимых способа** делать «лаг», и оба называются
`dart_lag_N`:

1. **Cutoff-anchored** (`CUTOFF_ANCHORED_LAG_HOURS = (1, 2, 3, 24)`,
   `features.py:62-64`): `lookup = ref_hour - Timedelta(hours=n-1)`, где
   `ref_hour` — последний известный час **на весь операционный день**
   (`last_known_hour_utc`, одно и то же значение для всех 24 часов
   поставки этого дня). Итог: `dart_lag_24` в текущем коде — одно
   константное число на весь день, а не «DART того же часа предыдущего дня»
   для каждого часа поставки отдельно.
2. **Row-anchored** (`TARGET_ANCHORED_LAG_HOURS = (48, 168)`,
   `features.py:70-72`): `dart.shift(n)` — обычный позиционный сдвиг,
   отдельное значение для каждой строки/часа поставки. Это ближе к тому,
   что описывает README (`dart_lag_24` = «тот же час предыдущего
   операционного дня»), но названо `dart_lag_48`/`dart_lag_168`, а не 24/48.

**Вывод:** ни `dart_lag_24`, ни `dart_lag_48` в текущем коде не совпадают по
смыслу с README §4. Значения, которые нужны README (`dart_lag_24`,
`dart_lag_48`, row-anchored), придётся построить заново тем же механизмом,
что сейчас используется для 48/168, но с других отступов — переиспользовать
имена нельзя, семантика разная.

### `dart.shift(n)` не защищён от дыр в индексе

`features.py:71-72` использует `.shift(n)` — это позиционный сдвиг на `n`
**строк**, не на `n` часов по времени. Сейчас индекс полный (0 пропусков,
раздел 1), поэтому сдвиг на 48/168 строк совпадает со сдвигом на 48/168
часов. Но Фаза 1 планирует `reindex` на полную сетку с явными `NaN` в дырах
(например, вокруг Winter Storm Elliott) — как только в индексе появятся
NaN-строки в середине истории (а не только в хвостах), позиционный
`.shift(n)` перестанет соответствовать `n` часам для всех строк после дыры.
Нужно проверить после Фазы 1, что `dart_lag_24`/`dart_lag_48` считаются
time-based сдвигом (по полному часовому индексу), а не позиционным.

### Cutoff — не 11:00 EPT, а 12:00 (полдень) ET

`features.py:7` — `DA_CLOSE_HOUR_ET = 12`. README §1 прямо говорит: окно
подачи заявок закрывается **в 11:00 EPT**. `last_known_hour_utc`
(`features.py:29-33`) считает `ref_hour` от полудня, а не от 11:00 — то есть
текущий код на час «щедрее» реального гейта. Это не проверяемая на текущих
данных утечка (RT LMP расчётного часа обычно публикуется вскоре после конца
часа), но при 11:00-гейте час `11:00–12:00 ET` предыдущего дня, скорее
всего, ещё не опубликован к моменту закрытия торгов — то есть нынешний код
может закладывать в признаки данные, которых участник рынка в реальности бы
не видел. Требует явной проверки при переписывании cutoff-функции в Фазе 1
(README §1 даёт готовую эталонную функцию `cutoff()`).

### Прогноз нагрузки

Не используется нигде. `data_collection.py` тянет только
`pjm_lmp_day_ahead_hourly` и `pjm_lmp_real_time_hourly` (строки 34-45) —
ни одного вызова `pjm_load_forecast_hourly_historical` или
`hrl_load_metered` в репозитории. Единственный экзогенный драйвер, который
требует README §2 и §4 (`load_fc_dom`, `load_fc_rto`, `load_fc_err_dom`,
`load_fc_err_rto`), отсутствует полностью — это весь объём Фазы 2.

| Признак | Доступен к 11:00 EPT D-1? | Комментарий |

## 3. Модели и оценка

### Сплит

Нет отдельного модуля. Единственное место — `analysis/models.ipynb`,
cell 16: `SPLIT_DATE = "2026-01-01"`, хардкод, двухчастный (train/test),
без validation. `data_collection.py:18-22` тоже хардкодит похожие, но не
идентичные по смыслу границы (`TRAIN_START/TRAIN_END/TEST_START/TEST_END`)
для скачивания сырых данных — то есть границы сплита продублированы в двух
местах (файл скачивания и ноутбук моделирования) и должны совпадать вручную.
README §6 требует трёхчастный сплит (train 2019-2023 / validation 2024 /
test 2025-2026-07) одной функцией, единственным источником границ — сейчас
нет ни того, ни другого.

### `score_backtest` / `score_direction`

`scripts/evaluation.py:29-73`. `score_backtest` — MAE/RMSE/MAE_rel по
колонкам-предсказаниям против `actual`. `score_direction` — accuracy/
precision/recall/F1, где положительный класс — `dart > 0`, то есть готовая
(но не используемая под классификацию спайков) регрессионная оценка знака.
**Ни одна из двух функций не вызывается ни в одном ноутбуке** — в
`analysis/models.ipynb` и `analysis/eda.ipynb` нет `import` из
`scripts.evaluation` (проверено grep по обоим файлам). Функции — мёртвый код
относительно текущего пайплайна; в Фазе 5 их придётся либо переписать под
precision/recall по `y_pos`/`y_neg` и P&L, либо оставить нетронутыми, если
их логика (MAE/RMSE) больше не целевая метрика (README §9 явно говорит: MAE/
RMSE не считать).

### Тесты

Нет. `find` по репозиторию не находит ни одного файла с тестами. Единственный
след — `scripts/__pycache__/backtest.cpython-312.pyc`, скомпилированный кэш
модуля `scripts/backtest.py`, которого больше нет ни в рабочем дереве, ни в
`git log --all` под этим путём с содержательной историей — не относится к
делу, можно игнорировать или почистить `__pycache__` (в `.gitignore` он и
так исключён).

## 4. Структура

### Дерево модулей

```
scripts/
  data/
    data_collection.py   fetch DA+RT LMP из GridStatus, посчитать dart, сохранить raw CSV
    features.py          build_features(): календарь + лаги + роллинги + сырые rt/da_lmp;
                          save_model_inputs(): X + таргет → CSV (запускается как __main__)
  models/
    baselines.py          персистентность (dart_lag_48) и seasonal-naive (среднее по hour-of-week)
    ridge.py               RidgeCV с StandardScaler, один fit на train, один predict на test
  evaluation.py            score_backtest (MAE/RMSE), score_direction (accuracy/precision/recall
                           по знаку dart) — сейчас не вызываются
analysis/
  eda.ipynb                разведочный анализ на сырых dart_data_*.csv, включая пример
                           mask_iqr_outliers для графиков (не сохраняет файлов)
  models.ipynb             читает train/test_features.csv, чистит через mask_iqr_outliers,
                           сохраняет features.csv, делает сплит, гоняет ridge+baselines
```

`scripts/data/data_processing.py` в рабочем дереве удалён — его единственная
функция (`save_model_inputs`) перенесена внутрь `scripts/data/features.py`
(видно по `git diff`, некоммичено). Дублирования сейчас нет.

### Точки входа

1. `python -m scripts.data.data_collection` — тянет данные из GridStatus API
   (платный/лимитированный вызов), пишет `dart_data_train.csv`,
   `dart_data_test.csv`.
2. `python -m scripts.data.features` — строит `train_features.csv`,
   `test_features.csv` из шага 1.
3. `analysis/models.ipynb`, руками, по ячейкам — читает вывод шага 2, чистит,
   сохраняет `features.csv`, обучает Ridge, строит графики.

Никакого единого CLI/orchestration-скрипта нет; порядок запуска не
формализован нигде, кроме этого документа.
